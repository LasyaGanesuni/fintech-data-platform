


# Auto Loader — Audit Framework & foreachBatch

## 1. Why do we need an Audit Framework?

Auto Loader handles the technical process of discovering and ingesting files.

However, in a production data platform, we also need to know:

- When did the pipeline run?
- Did the pipeline succeed or fail?
- How many records were processed?
- Which target table was populated?
- How long did the pipeline take?
- If it failed, what was the error?
- How can we trace a particular ingestion run?

This is the responsibility of the **audit framework**.

### Important distinction

Auto Loader's **checkpoint** and our **audit framework** serve different purposes.

```text
Checkpoint
    ↓
"What has this streaming pipeline already processed?"

Audit Framework
    ↓
"What happened during the pipeline execution?"
````

The checkpoint is used by Spark/Auto Loader for streaming state.

The audit framework is used by us for **operational visibility and monitoring**.

# 2. Existing Audit Framework

Our project already has:

```text
dbx_fintech_data_platform.metadata.ingestion_log
```

The table contains:

```text
pipeline_name
source_file
source_date
target_table
status
rows_processed
started_at
completed_at
error_message
```

This was originally designed for our file-level batch ingestion.

For example:

```text
pipeline_name
    = transaction_bronze_ingestion

source_file
    = transactions_00.csv

status
    = SUCCESS

rows_processed
    = 10000
```

This works well when the pipeline explicitly processes one file at a time.

---

# 3. Why Auto Loader is Different

With Auto Loader, we don't manually control individual files like:

```text
Read file 1
Check audit
Process file 1

Read file 2
Check audit
Process file 2
```

Instead:

```text
ADLS
 ↓
Auto Loader
 ↓
discovers new files
 ↓
creates streaming micro-batches
```

The checkpoint maintains the processing state.

Therefore, we should not recreate Auto Loader's file-tracking mechanism inside our audit framework.

Instead, the audit framework should provide **operational information about the pipeline execution**.

---

# 4. Run-Level Audit

For Auto Loader, we introduced the concept of a **pipeline run**.

A run represents one execution of the pipeline.

Example:

```text
Run ID: ABC123

Auto Loader execution
        ↓
   Batch 0
        ↓
   Batch 1
        ↓
   Batch 2
```

All these batches belong to the same pipeline execution.

A run-level audit can capture:

```text
run_id
pipeline_name
target_table
status
rows_processed
started_at
completed_at
error_message
```

---

# 5. Why do we need a `run_id`?

A single Auto Loader execution can process multiple micro-batches.

For example:

```text
Run ABC123
    │
    ├── Batch 0 → 100,000 rows
    └── Batch 1 → 140,500 rows
```

Without a `run_id`, it becomes difficult to group those batches into one pipeline execution.

The `run_id` gives us a common identifier:

```text
run_id = ABC123
```

So we can answer:

> "Show me everything that happened during this particular pipeline run."

---

# 6. What is a Micro-Batch?

Spark Structured Streaming processes streaming data in **micro-batches**.

Instead of thinking:

```text
240,500 rows
    ↓
one giant operation
```

think:

```text
Streaming Query
      ↓
┌──────────────┐
│   Batch 0    │
│ 100,000 rows │
└──────────────┘
      ↓
┌──────────────┐
│   Batch 1    │
│ 140,500 rows │
└──────────────┘
```

A micro-batch is a group of records processed together during one streaming execution step.

### Important

A micro-batch is **not necessarily the same thing as a file**.

A batch can contain:

* one file
* multiple files
* a subset of available records

depending on how Spark processes the stream.

---

# 7. What is `foreachBatch`?

`foreachBatch` allows us to execute our own custom function for every micro-batch generated by a streaming query.

Basic structure:

```python
def process_batch(batch_df, batch_id):
    # custom logic
```

Then:

```python
stream.writeStream \
    .foreachBatch(process_batch) \
    .start()
```

Conceptually:

```text
Auto Loader
     ↓
Batch 0
     ↓
foreachBatch()
     ↓
process_batch(batch_df, 0)

Auto Loader
     ↓
Batch 1
     ↓
foreachBatch()
     ↓
process_batch(batch_df, 1)
```

---

# 8. What does `batch_df` mean?

`batch_df` is the DataFrame containing the data for the current micro-batch.

For example:

```text
Batch 0
100,000 records
```

Inside the function:

```python
batch_df.count()
```

would return:

```text
100000
```

We can perform normal DataFrame operations on `batch_df`.

For example:

```python
batch_df.filter(...)
batch_df.select(...)
batch_df.count()
batch_df.write(...)
```

---

# 9. What does `batch_id` mean?

`batch_id` is Spark's identifier for the current micro-batch.

For example:

```text
Batch 0
Batch 1
Batch 2
...
```

So:

```python
def process_batch(batch_df, batch_id):
```

means:

> "Give me the current batch's data and its batch identifier."

---

# 10. Why use `foreachBatch`?

`foreachBatch` is useful when we need **custom logic for each micro-batch**.

For example:

```text
Auto Loader
     ↓
Micro-batch
     ↓
foreachBatch
     ↓
┌─────────────────────────┐
│ Count records            │
│ Write to Bronze          │
│ Write audit information  │
│ Perform custom logic     │
└─────────────────────────┘
```

Without `foreachBatch`, our Auto Loader pipeline can simply write directly to Delta.

With `foreachBatch`, we get control over what happens to each batch.

---

# 11. `foreachBatch` is NOT required for Auto Loader

This is important.

Our original Auto Loader implementation was:

```python
transactions_stream.writeStream \
    .format("delta") \
    .option("checkpointLocation", CHECKPOINT_LOCATION) \
    .trigger(availableNow=True) \
    .toTable(BRONZE_TABLE)
```

This is completely valid.

We only need `foreachBatch` when we want custom per-batch processing.

### Simple ingestion

```text
Auto Loader
    ↓
writeStream
    ↓
Delta Table
```

### Custom processing

```text
Auto Loader
    ↓
writeStream
    ↓
foreachBatch
    ↓
Custom Function
    ↓
Our logic
```

---

# 12. `.start()` vs `.toTable()`

This distinction is important when using `foreachBatch`.

## `.toTable()`

Example:

```python
stream.writeStream \
    .format("delta") \
    .toTable("bronze.transactions")
```

`toTable()` is a convenient streaming sink that writes the streaming data directly into a Delta table.

Conceptually:

```text
Streaming Data
      ↓
writeStream
      ↓
toTable()
      ↓
Delta Table
```

---

## `.start()`

`.start()` starts the configured streaming query.

It does not by itself mean:

> "Write to this table."

The configured sink determines what happens.

For example:

```python
stream.writeStream \
    .format("delta") \
    .start("/path")
```

or:

```python
stream.writeStream \
    .foreachBatch(process_batch) \
    .start()
```

With `foreachBatch`, the custom function decides what happens to the batch.

---

# 13. `.start()` with `foreachBatch`

Example:

```python
def process_batch(batch_df, batch_id):

    print(batch_df.count())
```

Then:

```python
query = (
    transactions_stream.writeStream
        .foreachBatch(process_batch)
        .start()
)
```

The flow is:

```text
Auto Loader
     ↓
Batch
     ↓
foreachBatch
     ↓
process_batch()
     ↓
Custom logic
```

If the function only contains:

```python
print(batch_df.count())
```

then nothing is written to a target table.

---

# 14. Writing to Bronze inside `foreachBatch`

If we want to write the batch to Bronze, we can explicitly do it inside the function:

```python
def process_batch(batch_df, batch_id):

    batch_df.write \
        .format("delta") \
        .mode("append") \
        .saveAsTable("bronze.transactions")
```

Now the flow becomes:

```text
Auto Loader
     ↓
Batch
     ↓
foreachBatch
     ↓
process_batch()
     ↓
Write batch
     ↓
Bronze Delta
```

Therefore:

> `.start()` starts the streaming query.
> `foreachBatch()` gives us control over each batch.
> The code inside the function determines what happens to that batch.

---

# 15. `.awaitTermination()`

Another method commonly used with `.start()` is:

```python
query.awaitTermination()
```

These have different responsibilities.

### `.start()`

Starts the streaming query.

### `.awaitTermination()`

Waits for the streaming query to finish or fail.

Example:

```python
query = (
    stream.writeStream
        .foreachBatch(process_batch)
        .trigger(availableNow=True)
        .start()
)

query.awaitTermination()
```

Flow:

```text
.start()
   ↓
Start query
   ↓
Process batches
   ↓
.awaitTermination()
   ↓
Wait until query finishes
```

With:

```python
.trigger(availableNow=True)
```

the query finishes after currently available data has been processed.

# 16. Auto Loader + Audit Concept

The complete conceptual flow is:

```text
                    ADLS
                      ↓
                 Auto Loader
                      ↓
                Micro-Batch
                      ↓
                foreachBatch
                      ↓
        ┌─────────────┴─────────────┐
        ↓                           ↓
   Write Bronze                 Audit
        ↓                           ↓
  Transaction Data            Run Information
```

The Bronze table stores the actual transaction records.

The audit table stores operational information about the pipeline execution.

---

# 17. Checkpoint vs Audit

This is one of the most important concepts.

### Checkpoint

```text
"What has already been processed?"
```

Used by Spark/Auto Loader.

Contains streaming state.

### Audit

```text
"What happened during the pipeline execution?"
```

Used by the engineering/operations team.

Contains information such as:

```text
run_id
status
rows_processed
start_time
end_time
error_message
```

Therefore:

```text
Checkpoint
    → Pipeline processing state

Audit
    → Pipeline operational visibility
```

They complement each other.

# 19. Important Production Consideration

`foreachBatch` gives us flexibility, but it also introduces responsibility.

For example:

```text
Write Bronze
    ↓
Write Audit
```

These are separate operations.

If Bronze succeeds but the audit write fails, the same streaming batch may be retried.

Therefore, custom audit logic inside `foreachBatch` must be designed carefully to avoid duplicate audit records.

A production-grade design should consider **idempotency for audit records**, potentially using a combination such as:

```text
run_id + batch_id
```

as the unique identity of a batch execution.

This is an important consideration for the next evolution of our audit framework.

# 20. Troubleshooting Lesson

During our Auto Loader implementation, the final Bronze table temporarily showed:

```text
491,000 records
```

This looked like Auto Loader had duplicated the data.

We checked the Delta table history.

Previous experiments had written:

```text
100,000
+ 140,500
+ 10,000
-----------
250,500
```

The final clean run wrote:

```text
100,000
+ 140,500
-----------
240,500
```

Therefore:

```text
250,500 + 240,500
= 491,000
```

### Root Cause

Previous experimental data had been written into the same target table.

It was **not Auto Loader reprocessing the source files**.

### Lesson

Keep independent pipelines isolated:

```text
Pipeline
├── Target Table
├── Checkpoint
└── Schema Location
```

Do not reuse streaming state or target tables between unrelated experiments.

# 21. Bronze Responsibility

Auto Loader's responsibility is ingestion.

Bronze should preserve the source.

Our source contained:

```text
240,500 records
240,000 unique transaction IDs
500 duplicate rows
```

Bronze therefore contains:

```text
240,500 records
```

The duplicate records are intentionally preserved.

# 24. Key Takeaways

### Auto Loader

> Handles incremental file discovery and ingestion.

### Checkpoint

> Maintains streaming processing state.

### Micro-Batch

> A group of records processed together by Structured Streaming.

### `foreachBatch`

> Allows custom logic to run for every micro-batch.

### `start()`

> Starts the configured streaming query.

### `toTable()`

> Directly writes streaming data to a Delta table.

### `awaitTermination()`

> Waits for a started streaming query to finish or fail.

### Audit Framework

> Provides operational visibility into what happened during pipeline execution.

### Bronze

> Preserves source data.

### Silver

> Handles cleaning, validation, deduplication, and business rules.

# 25. Interview Summary

A concise way to explain this design in an interview:

> "I use Databricks Auto Loader for incremental file ingestion from ADLS into Bronze. Auto Loader maintains file-processing state through the checkpoint. When I need custom processing at the micro-batch level, I use `foreachBatch`, which provides the current batch DataFrame and batch ID to a custom function. This allows us to implement additional logic such as audit capture or custom writes. The checkpoint handles streaming state, while our audit framework provides operational visibility such as run status, row counts, timings, and errors."
